# P06: native FDG exports, local distribution, Linux

This slice keeps the FDG solver in `src/layout.mojo`, the existing `GraphApp`,
and Moxi's existing SVG and native scene backends. It adds PNG/PDF conversion,
an example-local platform wheel, and a GTK/Linux entry point. The worker started
from `5db9a010053fd05412ee02d11eed05cce82b2a3c`; integration preserves the later
notebook and spatial changes. No notebook or shared Python packages were changed.

## Export contract

The native **Export…** command saves the current graph canvas, including current
positions, camera, selected-node outline, visible labels and neighborhood filter.
The search query remains application UI state: its selected result and filtering
are preserved; toolbar/search/status chrome is outside the exported canvas.
No layout step or fit happens during live export. The CLI/Python snapshot helper
instead creates a fresh deterministic layout (400 steps, then fit), as before.

`graph_export.mojo` sends the actual scene through `SvgSceneRenderer`. The
application-owned C writer invokes `rsvg-convert` for PNG/PDF, without a shell.
At 96 DPI, one scene unit becomes one PNG pixel or 0.75 PDF points. PDF text is
selectable. The supported FDG subset is rectangle, rounded rectangle, line,
text, clip and pop-clip. Images, gradients, paths and other unverified commands
raise an explicit error; there is no placeholder omission. Text uses an explicit
14-unit sans-serif style. Native system fonts, font fallback and antialiasing
can differ from librsvg; pixel-identical native typography is not promised.

Install an optional local `rsvg-convert` or set `MOXI_FDG_RSVG` to its executable.
SVG and the interactive viewer do not need it. Unsupported suffixes, a missing
converter, nonzero conversion, invalid output signatures and I/O failures are
reported. Output is written beside the destination and renamed only on success;
failed conversion preserves an existing destination. Temporary files are cleaned
on handled errors (forced process termination is not a cleanup guarantee).

```sh
bash examples/fdg/scripts/build.sh
examples/fdg/dist/moxi-fdg examples/fdg/examples/triangle.json --export /tmp/graph.png
examples/fdg/dist/moxi-fdg examples/fdg/examples/triangle.json --export /tmp/graph.pdf
```

```python
from moxi_fdg import ExportFormat, render_graph, sample_graph, view_graph
png = render_graph(sample_graph(), format=ExportFormat.PNG)
pdf = render_graph(sample_graph(), format=ExportFormat.PDF)
viewer = view_graph(sample_graph())
```

## Local package installation

Build the native executable first, then run `bash examples/fdg/scripts/package.sh`
(requires `uv`). Install the resulting exact platform wheel from
`examples/fdg/dist/wheels/` into a fresh venv. No editable install or source path
is needed. `moxi-fdg` is the console entry point. The wheel includes the executable,
sample JSON, Moxi license, three required Mojo runtime libraries and their original
license/notices. Wheel metadata identifies MIT plus the separate Modular license.
Runtime loader paths point inside the installed package.

The macOS wheel tag comes from the executable's real minimum deployment target;
this host generated `macosx_27_0_arm64`, not an unsupported older-macOS promise.
The Linux wheel is `linux_x86_64`, **not manylinux**. It requires compatible
Ubuntu 24.04 system libraries, GTK ≥4.14, an X11/Wayland display for native launch,
and the compiler's CPU requirements. GTK/system libraries are not bundled.
There is no runtime dependency download during install/import.

```sh
bash examples/fdg/scripts/clean-consumer.sh \
  "$PWD/examples/fdg/dist/wheels/moxi_fdg-0.1.0-py3-none-macosx_27_0_arm64.whl" \
  "$PWD/artifacts/demo-slideshows/fdg-clean-consumer"
```

This creates a retained `/tmp/moxi-p06-consumer.*` venv, installs only the wheel,
changes into a clean directory and uses `python -I` with Python/loader overrides
unset. It asserts that module and binary come from that venv, reads the packaged
fixture/notices, exports all formats, runs the native interaction replay and
console smoke, rejects missing optional converter and missing required runtime,
then restores and relaunches. The library audit checks installation-local Mojo
libraries. `/tmp/moxi-p06-consumer-path.txt` identifies the latest local install.

### Dependency licensing

[librsvg](https://github.com/GNOME/librsvg) is LGPL-2.1-or-later under its
[COPYING.LIB](https://github.com/GNOME/librsvg/blob/main/COPYING.LIB).
The exporter uses its separate `rsvg-convert` executable and does not bundle it.
Its [documented PNG/PDF and DPI options](https://github.com/GNOME/librsvg/blob/main/rsvg-convert.rst)
provide conversion after the existing Moxi SVG backend; no competing scene
exporter was added. Local macOS verification used librsvg 2.63.2.

The installed Mojo 1.1.0 compiler package declares
`LicenseRef-Modular-Proprietary`; its packaged license is the August 18, 2026
Modular MAX Community License. The build copies that exact LICENSE and
Third-Party-Notices from the installed compiler's package cache and fails if
missing. Loader paths/signatures are adjusted in the copied runtime binaries.
The newer [upstream MAX license](https://github.com/modular/modular/blob/main/Licenses/MAX_LICENSE)
is not assumed to retroactively replace the installed package license. These
are **local-use artifacts only**; external redistribution/license review,
notarization, distribution signing and public package publication remain gates.
The Python wrapper's standard-library-only runtime is unchanged; setuptools and
wheel are build-only. Pillow/PDFium are independent verification-only tools.

## Linux lane

The available Docker Desktop engine was already running on the ARM64 macOS host;
an existing Ubuntu 24.04 image could run amd64 with AVX/AVX2 visible under
emulation. A disposable `moxi-p06-linux` container was used. No VM or heavy host
service was started and no host settings were changed. Linux code compiles the
existing `native/linux_window.c` and `native/linux_text.c`, uses
`NativeWindow[BACKEND_LINUX]`, and adds FDG dialog/capture/export services. Linux uses the existing
`NativeFrameRenderer` ordered path; the legacy App surface clear is handled
outside its widget order. Initial runtime checks caught and corrected the
legacy canvas/surface mismatch rather than weakening the overflow check.
Independent visual review also found missing native graph labels: the shared
`NativeCanvasSceneRenderer` passed a Float64 literal to a C `float` font-size
argument. The one-line `Float32(14.0)` correction in `src/moxi/native_window.mojo`
is required by this lane. AppKit had masked the invalid value with its default
font size. Both platforms were rebuilt and recaptured after the correction.

The reproduction image uses Pixi 0.81.0 to match the lockfile producer. A newer
Pixi initially failed locked source-package identity validation; no lockfile
rewrite was made. GTK 4.14's software path runs under Xvfb with
`GSK_RENDERER=cairo`. This is a real Linux GTK runtime in an emulated container,
not physical Linux or a macOS/cross-compilation substitute.

```sh
# From repository root; opt-in disposable container, not a host service change.
docker build --platform linux/amd64 -f examples/fdg/Dockerfile.linux -t moxi-p06-linux-check .
docker run --name moxi-p06-reproduce --platform linux/amd64 moxi-p06-linux-check
# Copy evidence before removing the container.
docker cp moxi-p06-reproduce:/work/artifacts/demo-slideshows/fdg-linux \
  artifacts/demo-slideshows/
```

The Dockerfile-specific ignore file excludes host build/dist/Pixi caches. For an
existing Linux host with dependencies, run
`pixi run --locked bash examples/fdg/scripts/build-linux.sh`; the full container
check script also runs focused regressions, export assertions and native replay.
The image recipe is provided; acceptance below comes from the actual disposable
container with those dependencies, not a separately executed `docker build`.

## Verification and evidence

The finite `--replay EXISTING_DIRECTORY` mode runs the real native application,
sets search, dispatches Find/Neighbors, drag/cancel and zoom through its App event
routing, exports the current state, rejects `.jpg`, recovers with SVG and closes.
It requires a nonempty graph and cannot combine with `--export`/`--smoke`.
AppKit `cacheDisplay` and GTK widget snapshots are explicitly **offscreen-render**
captures of that running app, not native-window compositor screenshots.

Each of these directories has a schema-v1 `manifest.json`, export assertions,
and local ignored PNG/PDF/SVG/HTML artifacts:

- `artifacts/demo-slideshows/fdg-export`: source-built macOS export comparison.
- `artifacts/demo-slideshows/fdg-clean-consumer`: installed macOS wheel launch.
- `artifacts/demo-slideshows/fdg-linux`: Linux GTK/software replay.

Each sequence has initial search/neighborhood, interaction, saved result, reopened
PNG, independently rasterized PDF and recovery. `scripts/evidence.py` validates
and renders only those sequences through the existing shared slideshow functions;
it does not alter the shared gallery index. Manifests record the base revision,
scoped dirty status, individual source/PNG/artifact hashes, binary/wheel hashes,
reproduction and missing gates. Source inputs include the unchanged shared native
backends. Rebuild and recapture after integration; do not relabel dirty captures
as evidence of a later commit.

```sh
mkdir -p artifacts/demo-slideshows/fdg-export
examples/fdg/dist/moxi-fdg examples/fdg/tests/fixtures/export.json \
  --replay "$PWD/artifacts/demo-slideshows/fdg-export"
uv venv /tmp/moxi-p06-verify-env
uv pip install --python /tmp/moxi-p06-verify-env/bin/python Pillow pypdfium2
/tmp/moxi-p06-verify-env/bin/python examples/fdg/tests/verify_artifacts.py \
  artifacts/demo-slideshows/fdg-export
python3 examples/fdg/scripts/evidence.py fdg-export --host 'macOS ARM64' \
  --backend 'AppKit; cacheDisplay offscreen capture' --scale 2 \
  --binary examples/fdg/dist/moxi-fdg
```

Independent reopen checks parse SVG, decode PNG with Pillow, open PDF with
PDFium, extract all three Unicode labels, assert dimensions and five edge/loop
segments, compare three common node centers and raster difference. Visual
inspection also checks the actual native capture and reopened PDF. Exact native
font/pixel parity is deliberately outside this assertion.
The verifier also checks dark text ink in all three native label boxes and the
locations of native colored node cores against the exported geometry. Native
RGB equality is not asserted because AppKit applies color management.
