# Native assembly inspector (D07 / S3)

A second public `moxi_spatial` consumer: one transform hierarchy, linked perspective and orthographic views, shared selection and manipulation, two surface probes, and one clipping plane. The fixed four-object fixture is an assembly of generated surfaces, not imported CAD. All 3D camera, picking, constraints, preview/commit/cancel, history, measurement and clipping behavior is in the shared package. The app supplies layout, neutral object records, tool choice, native event routing and scheduling.

D05's performance/production renderer gate remains **OPEN**. This uses D06's experimental synchronous Metal render, CPU readback and owner-scoped copied-image composition. It is not a production recommendation or sustained 60 Hz result.

## Run and reproduce

```sh
bash examples/spatial-assembly/build.sh
./dist/spatial-assembly/assembly
bash examples/spatial-assembly/check.sh
python3 examples/spatial-assembly/gallery.py
```

The build uses the pinned Pixi Mojo environment when Mojo is absent from PATH. The check script builds both consumers and the public archive, runs the portable and native suites, precompiles both `moxi` and `moxi_spatial`, then compiles and replays **both complete applications** in a fresh `/tmp/moxi-d07-consumer.*` directory with only packaged Mojo imports. Native link inputs are the public spatial archive, each example's host object and the ordinary native text object. No source-tree import path is passed to these clean consumer builds.

Full check/build/replay logs use `/tmp/moxi-d07-*`. The gallery recipe writes only `artifacts/demo-slideshows/spatial-assembly`: tracked candidates `manifest.json`, `provenance.json`, `timing.json`; ignored PNGs and self-contained `index.html`. It uses the existing `scripts/demo_slideshows.py` validator/renderer and does not edit the master gallery or deferred status registry. Provenance records HEAD, scoped dirty files, individual source hashes, aggregate source hash, executable hash, tool versions and commands. Regenerate after source edits.

Select a hierarchy row or click a surface. O/P/S choose orbit/pan/select; X/R choose translation/rotation, and Scale is a button. Drag visible handles in either view. Numeric input applies a delta (scale uses a multiplier); arrows translate along world X. Escape cancels, Cmd-Z undoes, Shift-Cmd-Z redoes. Probe mode alternates endpoints on actual surface hits, across either view. The clipping controls enable the X plane and advance its offset. Dispose/Recreate affects only the right view; Slow geometry demonstrates bounded latest-result computation. The window is deliberately fixed at 1200 × 790 points, with two 440 × 390 viewports.

## Shared document and independent views

`SpatialViewport()` preserves the D06 independent-document behavior. `SpatialViewport(existing)` creates a new view of that document, with its own default camera, viewport, revision counters, lifecycle, owner and target. It shares object records, selection, history, mesh generation, manipulation state, probes, clipping, expanded geometry and GPU vertices. Cameras are explicitly configured by the app; linking does not copy camera state.

The C++ `Session` now owns small bounded view records. Each public handle activates its record before a synchronous main-thread call. There is one worker, one base mesh and one cached expanded vertex/triangle pair per document. View changes update projection state without rebuilding that geometry. Frames carry both view ID and lifecycle epoch; a frame from another view or retired lifetime fails the current-frame predicate. This is a focused shared-document extension, not a scene graph framework, ECS, CAD kernel or physics model.

The Metal bridge shares an `MSGeometry` allocation among renderers with the same nonreused document ID. One changed geometry serial uploads once; the other view consumes the same buffer. Each renderer still owns its color/depth target, pipeline/depth state, copied image, publication serial, timings and submission count. Those are real per-view allocations, not claimed as shared. The public composition seam and its ownership checks are unchanged; the inspector does not inject into a private image registry.

The replay's initial counters establish one generated mesh, one derived expansion, one upload, equal geometry identities, unequal composition target tokens, 18,240 expanded vertices and 583,680 shared GPU geometry bytes. The latter excludes targets, images and pipelines. Portable tests also compare the actual shared vertex/triangle storage addresses. Native tests mutate selection/geometry/clipping and change cameras independently, test origin-handle destruction, and close one native owner while the other keeps rendering from the same geometry allocation. Sixty two-view camera iterations add zero geometry uploads, zero derived rebuilds and zero control rebuilds. A 0.3-second idle sleep adds zero submissions.

## Hierarchy, probes and clipping contracts

- `SpatialNode(SpatialObject(...), parent)` adapts neutral instances to a bounded hierarchy. Parent zero means world. Nonzero stable application IDs are independent of list order; duplicates, zero IDs, missing parents, self/cyclic ancestry, invalid local transforms and invalid composed transforms reject the entire replacement without changing revision/history. IDs belong to the application; the library does not recycle or renumber them.
- Local transforms retain D06's uniform scale, Z rotation and translation. Composition rotates/scales the child translation, adds angles and multiplies scales. Local **and** world transforms retain the existing bounds. World-space handle/numeric operations convert to parent-local form at commit; descendants inherit preview and committed transforms. `transform` reads local values, `world_transform` reads composed values, both optionally including preview.
- One gesture owns the document at a time. Its originating view controls move/up/cancel; another view cannot steal it. A camera change in the other view preserves the gesture. Relevant document changes and origin camera/viewport changes cancel it. Both consumers use the existing constraint, snapping, operation validation and history state machines. Pointer capture loss, focus loss, Escape and resize route to cancellation in the app; no hardware acceptance is asserted.
- `probe(x,y)` alternates A/B anchors using the same clipped triangles as rendering and picking. `set_probe(SpatialEndpoint.A/B, id, local)` sets bounded finite local anchors explicitly (radius at most 2; it does not assert that an explicit point is on the surface). Distance is Euclidean in world units and follows hierarchy/preview changes. Missing endpoints/objects yield NaN. Probes are ephemeral, outside undo history, and clear when a new base mesh is accepted. A clipping change does not invalidate existing anchors; the measured geometric distance can span hidden surfaces. Cyan measurement and purple plane outlines are explicitly screen overlays, not depth-tested world geometry.
- `SpatialClip(enabled, normal, offset)` retains `dot(normal, world_point) >= offset`. Normal and offset are normalized together; zero/nonfinite normals and nonfinite/out-of-bound normalized offsets reject. There is no artificial cap. One shared CPU triangle clip produces up to two triangles per original triangle; those same triangles drive rendering, picking and annotation occlusion. A fully clipped document is a valid empty image. Clip enable/offset edits share document undo/redo; selection and probes do not create history entries. The public API accepts arbitrary normals; this app exposes the X plane only.
- Owner disposal retires only that view's target and gesture. Shared work/geometry survives while a sibling is live. Last-view disposal invalidates pending/completed generations; recreate schedules current work when needed. A disposed or failed origin handle can be destroyed without destroying a linked survivor. Owners cannot be rebound: create a fresh linked handle for a new owner. Work acceptance checks generation and shared revision; old results cannot replace the latest state or resurrect a disposed target.

Bounds remain 16 objects/document, 16 total public view handles (independent documents and links combined), 100,000 expanded vertices, 64 history entries, 32 composition resources and 2048 device pixels per dimension. Hierarchy depth is bounded by the object count. Clipping conservatively requires twice the uncut expanded vertex count to fit, even if a particular plane would remove most triangles; with this generator, 16 uncut objects fit but 16 clipped objects reject. Worker storage is bounded to one running, one latest pending and one completed result. Existing right-handed +Y world, top-left window coordinates, near/far 0.1/100 and main-thread public-call rules are preserved. `VERTICES` may populate the lazy shared expansion; read `FRAME_BUILDS` afterward when measuring it.

## Actual app glue and duplication

The inspector has 468 lines of Mojo including its synthetic replay (the replay starts at line 324; interactive entry point follows it), plus roughly 120 lines of native host glue. D06 remains 457 Mojo / 159 host lines and its source is unchanged. This is not a claim of zero duplicated app code:

- Both apps have their own 2D layout, tool buttons, event switch, numeric field handling, dirty scheduling and replay orchestration. The inspector has explicit left/right dispatch branches. These are app glue and are not counted as shared interaction implementation.
- The native shell repeats D06's small label/button/text parsing and AppKit capture/event-injection helpers. Inspector hit rectangles are its own layout data; ordinary drawing/focus uses the public native window setters. Direct AppKit canvas access is confined to capture and synthetic input hooks. The build includes the existing native host implementation just as D06 does.
- Both call the same public Mojo spatial wrapper, C ABI, portable manipulation/picking/projection implementation, worker and Metal bridge. No camera math, hit-ray algorithm, geometry generator, clipping algorithm or 3D gesture state machine was copied into the inspector.
- The demo-specific build/check/gallery scripts repeat bounded orchestration from D06. A generalized demo framework was not introduced for two examples. Each view still incurs rendering, depth storage, readback and image publication; reuse does not remove those costs.

The shared-file changes are limited to `native/spatial` and `src/moxi_spatial`. Hierarchy/clip/probe operations require the portable document and common triangle cache; linked handles require the C API ownership change; shared GPU vertices require the Metal bridge change. Neither the composition seam nor general native window implementation changes. The D06 portable/native suites and complete clean packaged replay are mandatory regressions.

## Evidence and remaining gates

The fourteen real captures cover initial views, independent camera navigation, hierarchy preview/commit, cross-view surface measurement, clipping and offset undo, Escape cancellation, numeric input, stale worker rejection, disposal and recreation. Captions describe the actual replay. Captures use AppKit `cacheDisplay` and are labeled **offscreen-render**, not compositor/native-window evidence. The native test additionally exercises separate native owners; the gallery's two targets share one owner.

`timing.json` records 60 samples per view and sequential two-call phase sums: process CPU, encode, command wait, GPU timestamps, readback, publication and frame-to-host-image total. Samples are nearest-rank distributions and include raw values. Phase intervals overlap. Pair sums exclude application/inter-call overhead; totals end before AppKit presentation, compositor and scanout. Concurrent system/worker activity is uncontrolled. No memory residency/thermal/energy run, sustained 60 Hz run, production recommendation, physical input, human acceptance, IME, VoiceOver or compositor proof is claimed. VoiceOver remains paused. Local browser gallery verification establishes gallery behavior only.

Focused validation results and browser checks are recorded separately in the artifact directory so they do not change the source fingerprint after capture. Confidence in the bounded implementation is high given portable, native, clean consumer and replay evidence; larger real assemblies, imported meshes, sustained load, real input/accessibility checks and production renderer evidence could change that assessment. D05 stays open regardless of these local passing checks.
